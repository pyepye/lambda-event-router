APIGatewayMatcher ​

APIGatewayMatcher routes Amazon API Gateway requests to handlers, one request per invocation.

Your routes are matched on method and path, your handler returns a body, and the matcher turns that into a status code and a response AWS understands. It takes REST API events and both HTTP API payload versions, and hands your handler the same request object whichever one arrives.

Install ​

bash
npm install @latcher/base @latcher/apigateway

@latcher/base is a peer dependency, so install it yourself. It exports Latcher, which every matcher plugs into.

@latcher/http comes along as a dependency. The shared HTTP types, HTTPMiddleware among them, are re-exported from here.

Create the matcher ​

ts
import { createAPIGatewayMatcher } from '@latcher/apigateway'
import { withRequestLog } from './middleware/withRequestLog'

const apiMatcher = createAPIGatewayMatcher({
  responseType: 'json',  // Optional
  errors: {  // Optional
    json: ({ statusCode, message }) => ({ status: statusCode, message }),
  },
  middleware: [withRequestLog],  // Optional
  cors: { origin: 'https://app.example.com' },  // Optional
})

Every option can be left out. createAPIGatewayMatcher() on its own gives you a matcher that answers JSON, answers 404 for anything you have not registered and sends no CORS headers.

Options ​

OptionTypeRequiredDefaultDescription
authAuthPresetNoThe preset every route uses unless it names its own. See auth presets
responseTypeResponseTypeOptionNo'json'What every route answers with unless it names its own. See response types
errorsErrorFunctionsNoBuilds the body of every error response, one function per kind. Required when the matcher serves HTML. See error responses

Register routes ​

ts
apiMatcher.route({
  filters: {
    method: 'POST',
    path: '/orgs/:orgId/orders',
  },
  querySchema: CreateOrderQuerySchema,  // Optional
  bodySchema: NewOrderSchema,  // Optional
  middleware: [withOrgContext],  // Optional
  responseType: 'json',  // Optional
  responseSchema: OrderSchema,  // Optional
  handler: createOrder,
})

filters and handler are the only required keys, and inside filters both method and path are required. A responseType on the route overrides the matcher's, so one matcher can mix response types.

route() returns the matcher, so you can chain registrations.

ts
apiMatcher.route(createOrderRoute).route(getOrderRoute)

Method and path are both part of the match, so two routes only compete when they share a method and their paths overlap. GET /orders/:orderId and POST /orders/latest never collide.

Where they do share a method, routes match by path specificity rather than registration order: a literal segment beats a param at the same position, compared left to right. So GET /orders/latest takes /orders/latest while GET /orders/:orderId catches every other id, whichever order you register them in. A segment that mixes literal text with a param sits between the two, so /files/:name.json beats /files/:id for /files/report.json. Two routes of the same shape differing only in a param name, such as GET /orders/:orderId and GET /orders/:id, match the same paths and cannot be ranked, so the one you registered first wins and the second never runs. Giving one of them a custom ranks it first, because a custom can only reject a request and never accept an extra one. See match order.

When nothing matches, the matcher answers 404 and runs no middleware. A JSON matcher sends {"error":"Not Found"}, and any other matcher sends its own error response. A path you have registered under another method counts as no match rather than a 405, so DELETE /orders/1 against a GET /orders/:orderId route answers 404. See nothing matched for what the other matchers do instead.

route() types body from the method filter. A POST, PUT or PATCH route gets unknown and the other four get undefined, the same as the convenience methods. A bodySchema replaces either with the schema output.

Convenience methods ​

get(), post(), put(), patch(), delete(), head() and options() fill in the method filter and take everything else exactly as route() does.

ts
// Both of these register the same route
apiMatcher.get({
  filters: { path: '/orders/:orderId' },
  handler: getOrder,
})

apiMatcher.route({
  filters: { method: 'GET', path: '/orders/:orderId' },
  handler: getOrder,
})
MethodSetsTypes body as without a bodySchema
get()method: 'GET'undefined
post()method: 'POST'unknown
put()method: 'PUT'unknown
patch()method: 'PATCH'unknown
delete()method: 'DELETE'undefined
head()method: 'HEAD'undefined
options()method: 'OPTIONS'undefined

Every method takes a bodySchema, and body is then the schema output. Each method rejects a method in its filters. See convenience methods for how the other matchers use them.

A GET, HEAD, DELETE or OPTIONS route without a bodySchema never parses the body, so the handler gets undefined even when the client sends one. Add a bodySchema if the route needs it. See request body for when the matcher parses it.

An options() route wins over the automatic CORS preflight, which is how you take over answering a preflight for one path.

A HEAD response never sends a body. HTTP says a HEAD response carries no content, so the matcher drops the body and keeps the status code and headers. Return a value or NoContent(), either way the body is stripped.

Filters ​

Every filter key on one route. method and path are required, and custom is the only optional one.

ts
apiMatcher.route({
  filters: {
    method: 'POST', // Or lower case, so 'post' works too
    path: '/orgs/:orgId/orders',
    custom: ({ headers, auth }) => {
      // Only a custom reaches the headers, the auth or the raw event
      return headers['x-api-version'] === '2' && auth?.type === 'jwt' && auth.scopes?.includes('orders:write') === true
    },
  },
  bodySchema: NewOrderSchema,
  handler: createOrder,
})
FilterTypeDescription
methodAnyHttpMethodThe request method. Lower case is uppercased for you, so 'get' and 'GET' register the same route
pathstringA path pattern, with :name marking each param. Not a FilterStringMatcher
custom(input: HTTPFilterInput) => boolean | Promise<boolean>Given { method, path, headers, multiValueHeaders, query, multiValueQuery, body, auth, event }, where path is the raw path string and body is the request body before parsing. Can be async

method and path are the whole of the built in matching, which is why headers and auth are worth a custom here where they would be a filter key on another matcher.

custom sees the body as an unparsed string and no schema has run, so parse it yourself if you need it, and prefer the request object for anything you only want once a route has matched. See custom for where it sits in the filter order.

Path patterns ​

A :name param matches text inside one segment and gives your handler that value under name. The name uses ASCII letters, digits, _ and $, and can't start with a digit. It ends at the first character outside that set, so /files/:name.json has a param called name followed by the literal text .json.

PathParams reads the same syntax to type request.path. For /orders/:orderId your handler gets request.path.orderId typed as a string.

PatternRequestrequest.path
/orders/:orderId/orders/9{ orderId: '9' }
/orgs/:orgId/orders/:orderId/orgs/acme/orders/9{ orgId: 'acme', orderId: '9' }
/orgs/:orgId/orders/orgs/acme/orders{ orgId: 'acme' }
/orders/:orderId/orders/9/itemsNo match, a param stops at the next /
/orders/orders/{}, a trailing slash comes off both sides
/orders/{orderId}/orders/9No match
/orders/{orderId}/orders/{orderId}{}
/files/:name.json/files/report.json{ name: 'report' }
/files/:name.json/files/report.txtNo match, .json is literal text
/api/v:version/api/v2{ version: '2' }
/files/:name.:ext/files/a.b.json{ name: 'a.b', ext: 'json' }
/v1.0/orders/v1X0/ordersNo match, the . is a literal dot

The two {name} rows are traps rather than features.

{name} is not path param syntax here. API Gateway's own console and CDK both use braces, so it looks right and it compiles. It is a literal, which types nothing and matches only a request for that exact string. Use :orderId.

A : without a valid name after it throws when you register the route. /items/:1abc and /items/: both throw. TypeScript also flags them on the path filter, so you see the mistake in your editor first.

A non-ASCII letter ends the name. /:café has a param called caf followed by the literal text é.

When two params share a segment, the first one takes any extra text. /files/:name.:ext gives name as a.b and ext as json for /files/a.b.json.

A ., + or other regex metacharacter in a literal segment matches itself. The literal parts of a pattern are escaped before it is compiled to a regular expression, so /v1.0/orders matches /v1.0/orders and nothing else.

Handler ​

Handlers take one argument and return the body they want on the wire.

ts
import type { ApiRequest, HandlerResponse } from '@latcher/apigateway'
import { NotFound, Ok } from '@latcher/apigateway'

export async function getOrder(
  request: ApiRequest<{ orderId: string }>,
): Promise<HandlerResponse<Order>> {
  const order = await orders.get(request.path.orderId)
  if (!order) {
    throw NotFound(`Order ${request.path.orderId} not found`)
  }

  return Ok(order)
}

Request object ​

FieldTypeDescription
methodstringThe request method, upper case
pathTPathThe params named in the route's path pattern. Empty when the pattern names none
rawPathstringThe path string the caller asked for, the same on a 1.0 or 2.0 payload
queryTQueryQuery string params, one value per key. Where a name repeats, this is the last value
multiValueQueryRecord<string, string[] | undefined>Every value for each query param, in the order they arrived
bodyTBodyThe parsed body. See request body for when the matcher parses it. A body that is not valid JSON arrives as the raw string, a binary body as a Buffer, and no body at all as null
rawBodystring | undefinedThe body exactly as the service sent it, still base64 where isBase64Encoded is true
isBase64EncodedbooleanWhether the service base64 encoded the body it sent
headersRecord<string, string | undefined>Request headers. Read them lower cased. Where a name repeats, this is the last value
multiValueHeadersRecord<string, string[] | undefined>Every value for each header, lower cased key

eventAPIGatewayEventThe untouched event from AWS, for requestContext, stageVariables and anything else you need

Context comes from aws-lambda, not from this package. APIGatewayEvent types event and is exported from here.

path holds the params rather than the path itself. Read request.rawPath when you want the string the caller asked for. It reads the same on a 1.0 or 2.0 payload, so you don't have to reach into the event and branch on the version.

The Content-Type header on the request decides the shape of body. The matcher decodes base64 for you, so you never check the flag yourself.

Content-TypeWhat you get in body
Anything holding json, xml or yaml, such as application/json or application/vnd.api+jsonThe parsed value, or the raw string when it will not parse
text/*, application/x-www-form-urlencoded, application/javascript or application/graphqlThe string
Anything else, such as image/png, application/gzip or application/octet-streamA Buffer of the bytes that were sent

A route's body type stays the same however the caller sent it, so a route taking bytes gets a Buffer whether or not the body arrived base64 encoded. See binary bodies for typing one.

A request with no Content-Type header gives you the string. The one exception is a base64 body holding bytes utf-8 cannot carry, which you get as a Buffer because a string would lose them.

The matcher lowercases header names, so you read the header itself back as request.headers['content-type'].

request.rawBody holds the body exactly as the caller sent it, still base64 when request.isBase64Encoded is true. You need it about as often as you need request.event.

A REST API (1.0) payload carries every value for a repeated query param or header, so request.multiValueQuery and request.multiValueHeaders give you the full list while query and headers keep the last value.

An HTTP API (2.0) payload does not. AWS comma joins repeated values into one string before it reaches you, so ?tag=a&tag=b arrives as query.tag of 'a,b'. We do not split that back apart, since a value can hold a comma of its own, so on a 2.0 payload multiValueQuery.tag is the single entry ['a,b'].

Request body ​

The matcher parses the body only when the route needs it. This means a route that ignores the body does not spend time or memory on JSON.parse.

RouteWhen the matcher parses the bodybody
Any method with a bodySchemaBefore the handler runs, to validate itThe schema output
POST, PUT or PATCH without a bodySchemaThe first time something reads request.bodyunknown
GET, HEAD, DELETE or OPTIONS without a bodySchemaNeverundefined

A middleware that copies the request with { ...request } reads body, so the parse happens there rather than in the handler. It still happens only once.

Response type ​

HandlerResponse<T> is ApiResponse<T> | T | HTTPException, where T is the body the route's response type takes. You can return the body on its own, a full { statusCode, body, headers } or an error helper. It defaults to a JSON body. See Responses for what the matcher does with each.

Inferred handlers ​

Nothing to look up and nothing to keep in sync. defineRoute reads the path pattern and the schemas and hands your handler a typed path, query and body, so orgId and orderId below are both string and body matches NewOrderSchema without you declaring either.

ts
import { logger } from '@latcher/base'
import { defineRoute, Ok } from '@latcher/apigateway'
import { z } from 'zod'

const NewOrderSchema = z.object({ sku: z.string(), quantity: z.number() })

export const replaceOrderRoute = defineRoute({
  filters: { method: 'PUT', path: '/orgs/:orgId/orders/:orderId' },
  bodySchema: NewOrderSchema,
}).handle(async ({ path, body }) => {
  const order = await orders.replace(path.orgId, path.orderId, body.sku, body.quantity)
  logger.info(`Replaced order ${path.orderId} for org ${path.orgId}`)

  return Ok(order)
})

apiMatcher.route(replaceOrderRoute)

route() and the convenience methods infer the same types from the same schemas, so the choice between the two forms is about where your code sits rather than what it is typed as.

Inference is only as good as the path pattern, so read path patterns before relying on path being typed.

Inference pays off most in a Lambda taking several event sources, since you never have to know any of their request shapes. See inferred handlers, where the same queue is written both ways to compare.

Annotated handlers ​

Annotating the request yourself splits route setup from business logic, using ApiRequest and your own types.

ts
// handlers/orders.ts
import type { APIGatewayAuth, ApiRequest, HandlerResponse } from '@latcher/apigateway'
import { Created } from '@latcher/apigateway'
import { z } from 'zod'

export const NewOrderSchema = z.object({ sku: z.string(), quantity: z.number() })
type NewOrder = z.infer<typeof NewOrderSchema>

export async function createOrder(
  request: ApiRequest<{ orgId: string }, Record<string, string | undefined>, APIGatewayAuth, NewOrder>,
): Promise<HandlerResponse<Order>> {
  const { orgId } = request.path
  const { sku, quantity } = request.body

  return Created(await orders.create(orgId, sku, quantity))
}
ts
// api.ts
import { createAPIGatewayMatcher } from '@latcher/apigateway'

import { createOrder, NewOrderSchema } from './handlers/orders'

const apiMatcher = createAPIGatewayMatcher()

apiMatcher.post({
  filters: { path: '/orgs/:orgId/orders' },
  bodySchema: NewOrderSchema,
  handler: createOrder,
})

Derive the type from the schema with z.infer rather than hand-writing an interface that mirrors it.

The handler's annotation does not type the body on its own. Only the bodySchema or the method does, so createOrder above does not compile on a route without bodySchema: NewOrderSchema. Annotated handlers has the worked version.

For the path you can do the same with PathParams<'/orgs/:orgId/orders/:orderId'>, which reads the params out of the pattern so you are not keeping a second copy of it in step. Check it against path patterns first, since a pattern ending in a literal segment gives you nothing and writing the type out by hand is the answer there.

ApiRequest takes its parameters in the order TPath, TQuery, TAuth, TBody, so typing only the body means passing the query and auth types through as well. Generic parameters has each one, its default and which types take them in a different order.

Schema validation ​

Three keys take a schema, and all three are optional.

ts
const OrderQuerySchema = z.object({ expand: z.string().optional() })
const NewOrderSchema = z.object({ sku: z.string(), quantity: z.number() })
const OrderSchema = z.object({ orderId: z.string(), sku: z.string(), quantity: z.number() })

apiMatcher.route({
  filters: { method: 'POST', path: '/orgs/:orgId/orders' },
  querySchema: OrderQuerySchema,
  bodySchema: NewOrderSchema,
  responseSchema: OrderSchema,
  handler: createOrder,
})
KeyValidatesA failure answers
querySchemaThe query string params400, with the validation issues as the context
bodySchemaThe parsed request body422, with the validation issues as the context
responseSchemaThe body of every 2xx response the handler returns500

Any Standard Schema library works. Validation runs after a route has matched, so a request failing its schema gets an error response rather than falling through to the next route, and no middleware runs. The query is checked first, so a request with a bad query and a bad body gets the 400.

Both failures put the issues array in the error response as its context, so on a JSON route the caller sees the schema library's own messages and paths.

json
{ "error": "Unprocessable Content", "context": [{ "code": "invalid_type", "path": ["quantity"], "message": "Invalid input: expected number, received string" }] }

The handler receives the schema output. A querySchema of z.object({ page: z.coerce.number().default(1) }) hands query.page the number 2 for ?page=2 and 1 when the param is absent, and unknown keys are stripped.

responseSchema checks every 2xx the handler returns, so Ok(order), { statusCode: 200, body: order } and a bare order are all checked, and the caller gets the schema output. A 204 is checked too, so NoContent() on a route whose schema needs a body answers 500. An error or a redirect is sent without the check.

Its output has to match the route's kind, so a JSON route's responseSchema outputs a JSON body and an HTML route's outputs Html.

Binary bodies ​

A route that takes bytes says so with BinaryBody. It types request.body as a Buffer and answers 422 when the request's Content-Type is one the matcher reads as text.

ts
import { BinaryBody, defineRoute, Ok } from '@latcher/apigateway'

export const uploadLabel = defineRoute({
  filters: { method: 'PUT', path: '/labels/:labelId' },
  bodySchema: BinaryBody,
}).handle(async (request) => Ok({ bytes: request.body.length }))

It is a Standard Schema like any other, so an annotated handler works the same way. Type its body as Buffer and a signature that disagrees with the schema fails the compile.

Leave the bodySchema off and body is unknown, which the compiler makes you narrow with Buffer.isBuffer(request.body) before you can use it.

Responses ​

Return a value and the matcher works out the status code, encodes the body and sets its content type. What you can return depends on the route's response type, which is JSON unless you say otherwise.

ts
return { orderId: order.orderId }             // 200, with a JSON content type
return Ok({ orderId: order.orderId })         // The same 200
return { statusCode: 200, body: order }       // Also the same 200

On a JSON route:

You returnYou get
An object or an array, {} included200, with a JSON content type
undefined or null204
A string, a number or a booleanA compile error. At runtime it is JSON-encoded, so 'ok' goes out as "ok"
A Buffer, a Uint8Array or an ArrayBufferA compile error, since bytes need a binary route
A value JSON cannot carry, such as a function or an object that refers to itself500, and the matcher logs it

A Map or a Set does not compile either, because JSON.stringify would send it as {}.

Response types ​

A route answers in one of four kinds. Set responseType on the matcher for its default and on a route to override it, so one matcher can serve both pages and a JSON API.

ts
import { createAPIGatewayMatcher, Html } from '@latcher/apigateway'

const apiMatcher = createAPIGatewayMatcher({
  responseType: 'html',
  errors: { html: ({ statusCode, statusText }) => Html(`<h1>${statusCode} ${statusText}</h1>`) },
})

apiMatcher
  .get({
    filters: { path: '/orders/:orderId' },
    handler: async ({ path }) => Html(nunjucks.render('order.njk', await orders.get(path.orderId))),
  })
  .get({
    filters: { path: '/api/orders/:orderId' },
    responseType: 'json',
    handler: async ({ path }) => orders.get(path.orderId),
  })
  .get({
    filters: { path: '/health' },
    responseType: 'text',
    handler: async () => 'ok',
  })
KindThe handler returnsSent asDefault content type
jsonAn object, an array, null or undefinedJSONapplication/json
htmlHtml(...)The string as it istext/html; charset=utf-8
textA stringThe string as it istext/plain; charset=utf-8
binaryA Buffer, a Uint8Array or an ArrayBufferBase64, with isBase64Encoded setapplication/octet-stream

The compiler checks the handler against its kind, so a plain string on an HTML route or an object on a text route fails the build. Html() is the only way to make an HTML body, which means a string never reaches a page unless you wrap it. It takes a promise too, and then gives you a Promise<Html>.

An HTML route needs errors.html on its matcher, because no default error page could match your site. Leave it out and the route fails the compile, and the matcher throws when you register it. See error responses for writing one.

When the content type differs from the kind's default, pass { type, contentType } instead. A json kind takes only a JSON content type, such as application/problem+json, and the other kinds take anything else.

ts
apiMatcher.get({
  filters: { path: '/reports/orders.csv' },
  responseType: { type: 'text', contentType: 'text/csv' },
  handler: async () => orders.csv(),
})

An empty string on a text route is a 200 with an empty body, and undefined or null is a 204 on every kind.

A REST API sends a binary response as bytes only when the first type in the request's Accept header is in its binaryMediaTypes. Otherwise the caller gets the base64 text, whatever the response's Content-Type. Setting binaryMediaTypes to ['*/*'] sends the bytes for every request. An HTTP API sends the bytes for every request with no setting.

A content-type header on a single response sets the content type for that response alone, so a JSON route can answer Ok(problem, { 'content-type': 'application/problem+json' }). Through Ok() and Created() the compiler checks the header against the body: a JSON content type takes a JSON body, and any other takes a string or bytes. The body still has to suit the route's kind, so a CSV string needs a text route.

Response helpers ​

Anything other than a 200 or a 204 goes through a helper, or you set the status code yourself. The success helpers take the body. The error helpers take a message and a context, both optional, and the matcher turns them into an error response.

HelperStatusWith no arguments
Ok(body, headers?)200The body is required
Created(body, headers?)201The body is required
NoContent()204Empty
TemporaryRedirect(location)307Empty, with a Location header
PermanentRedirect(location)308Empty, with a Location header
BadRequest(message?, context?, headers?)400The message Bad Request
Unauthorized(message?, context?, headers?)401The message Unauthorized
Forbidden(message?, context?, headers?)403The message Forbidden
NotFound(message?, context?, headers?)404The message Not Found
Conflict(message?, context?, headers?)409The message Conflict
UnprocessableContent(message?, context?, headers?)422The message Unprocessable Content

On a JSON route the message goes out as error, and the context, when there is one, as context.

ts
throw NotFound(`Order ${path.orderId} not found`)
// 404 {"error":"Order ord-1 not found"}

throw Conflict('Shipped orders cannot be cancelled', { orderId: path.orderId, status: order.status })
// 409 {"error":"Shipped orders cannot be cancelled","context":{"orderId":"ord-1","status":"SHIPPED"}}

The context can be any JSON value, and the compiler rejects one JSON cannot carry, such as a Map.

For an error status with no helper, throw an HTTPException with the status first. It takes only a 4xx or 5xx, so any other status fails the compile. For any other status, return an ApiResponse yourself. HTTP_STATUS_CODES is exported if you would rather not write the number.

ts
import { HTTP_STATUS_CODES, HTTPException } from '@latcher/apigateway'

throw new HTTPException(HTTP_STATUS_CODES.SERVICE_UNAVAILABLE, 'Down for maintenance', undefined, {
  'retry-after': '3600',
})

return { statusCode: HTTP_STATUS_CODES.ACCEPTED, body: { jobId } }

Throwing ​

Throwing a helper works the same as returning it, and it carries the same weight from any depth, so a function three calls below your handler can end the request without every function in between passing a failure back up.

ts
import { Conflict, NotFound } from '@latcher/apigateway'

const order = await orders.get(path.orderId)
if (!order) throw NotFound(`Order ${path.orderId} not found`)
if (order.status === 'SHIPPED') throw Conflict('Shipped orders cannot be cancelled')

Anything else thrown becomes a 500 with Internal Server Error as the message. The matcher logs the error with its own message, so a new Error('connect ETIMEDOUT 10.0.1.5:8000') ends up in your logs and never on the wire.

Error responses ​

The matcher builds every error response the same way, whether a handler threw a helper or the matcher hit the error itself.

ErrorStatusmessagecontext
No route matched404Not FoundNone
Auth missing401UnauthorizedNone
Auth invalid403ForbiddenNone
Auth preset error500Internal Server ErrorNone
Query fails querySchema400Bad RequestThe schema issues

An error helper or HTTPExceptionIts statusYours, or the helper's defaultYours

With no error function of your own, a JSON route sends the message as error and adds the context as context when there is one. A text route sends the message on its own.

json
{ "error": "Unprocessable Content", "context": [{ "code": "invalid_type", "path": ["quantity"], "message": "Invalid input: expected number, received string" }] }

To send your own shape, set errors on the matcher with a function per kind. json and text are optional, and html is required on a matcher with any HTML route.

ts
import { createAPIGatewayMatcher, Html } from '@latcher/apigateway'

const apiMatcher = createAPIGatewayMatcher({
  responseType: 'html',
  errors: {
    html: ({ statusCode, statusText }) => Html(`<h1>${statusCode} ${statusText}</h1>`),
    json: ({ statusCode, message, context }) => ({ statusCode, error: message, details: context }),
  },
})

The html function above returns only an <h1> heading. To send a full HTML page, use a template engine such as Nunjucks.

Each function gets the same input and returns only the body. The status comes from the error, and the headers from the HTTPException or helper that raised it.

FieldTypeDescription
statusCodeErrorStatusCodeThe status, from 400 to 599
statusTextstringThe name of the status, such as Not Found
messagestringThe message the error was given, or its default
contextErrorContext | undefinedThe context the error was given, or the schema issues for a 400 or 422

The matcher calls the function for the route's kind, and the matcher's kind for a 404 that matched no route. A binary route never sends bytes as an error, so it uses the matcher's kind, and a binary matcher uses JSON.

An error response takes its kind's default content type rather than the route's, so a text/csv route's 404 is text/plain. Set a content-type in the exception's headers to change it.

If an error function throws, the matcher logs it and answers a 500 it builds itself. A JSON route gets {"error":"Internal Server Error"}, and every other kind gets the plain text Internal Server Error.

CORS headers and the HEAD rule apply to every error response.

Auth ​

request.auth holds whatever authorised the request, in the same shape whichever API and payload version it came through. It is undefined on an unsecured route.

Check auth.type first, and TypeScript narrows auth to that variant.

ts
async function listOrders({ auth }: ApiRequest) {
  if (auth?.type !== 'jwt') throw Unauthorized()

  const groups = auth.claims['cognito:groups'] ?? [] // string[]
  // ...
}
typeComes fromFields
lambdaA Lambda authorizer, on either APIprincipalId, context
cognitoA Cognito user pool authorizer on a REST APIclaims
jwtA JWT authorizer on an HTTP APIclaims, scopes
iamIAM authorisation, on either APIiam
apiKeyAn API key on a REST API, with no authorizerapiKey
clientCertMutual TLS, with no authorizerclientCert

An API key and a client certificate can arrive alongside any authorizer. Every variant has optional apiKey and clientCert fields, so auth?.apiKey?.id works whatever type is.

Auth presets ​

A preset tells the matcher which authorizer a route sits behind, and checks the request against it. Your handler then gets that variant already narrowed, so there is no auth.type check to write.

ts
import { createAPIGatewayMatcher, iamAuth, lambdaAuth, noAuth } from '@latcher/apigateway'
import { z } from 'zod'

const orgAuth = lambdaAuth(z.object({ orgId: z.string(), seats: z.coerce.number() }))

const apiMatcher = createAPIGatewayMatcher({ auth: orgAuth }) // every route uses orgAuth unless it names its own

apiMatcher.get({
  filters: { path: '/orders' },
  handler: async ({ auth }) => orders.list(auth.context.orgId, auth.context.seats), // seats is a number
})
apiMatcher.get({ filters: { path: '/audit' }, auth: iamAuth(), handler: readAudit })
apiMatcher.get({ filters: { path: '/health' }, auth: noAuth(), handler: health })
PresetAcceptsTakes
lambdaAuth(schema?)A Lambda authorizerA schema for context
cognitoAuth({ claims })A Cognito user pool authorizerA schema for the claims you rely on
jwtAuth({ claims })A JWT authorizerA schema for the claims you rely on
iamAuth()IAM authorisationNothing
noAuth()Anything, and hands your handler undefinedNothing

Put noAuth() on a public route to take it out of the matcher default.

A claims schema only needs the claims you care about. The matcher lays its output over the claims that arrived, so sub, exp and the rest are still there.

A request that fails its preset does not reach the handler. The status depends on the failure:

FailureStatusLogged as
No auth arrived401A warning
The schema refused the context or the claims403A warning
A different authorizer ran, such as IAM on a lambdaAuth() route500An error

A different authorizer can only come from the API Gateway setup and the code disagreeing, so the caller gets a 500 and nothing about why. Every log names the preset, the reason and any schema issues. The response body is the default one from Unauthorized(), Forbidden() or InternalServerError().

The check runs after the route matches, and before query and body validation. A custom filter runs before the check, so it sees auth as it arrived. Middleware and the handler see the checked auth.

noAuth() logs a warning when auth arrives anyway, because that means an authorizer is attached to a route the code treats as public.

A preset is a plain value, so define it once and import it wherever it is needed. For an annotated handler, AuthOf reads the auth type off a preset.

ts
import type { ApiRequest, AuthOf } from '@latcher/apigateway'

import { orgAuth } from './auth.js'

export async function listOrders({ auth }: ApiRequest<{}, Query, AuthOf<typeof orgAuth>>) {
  return orders.list(auth.context.orgId)
}

An annotated handler only compiles on a route that promises the auth it expects. That means a route with the same preset, or a matcher whose default is that preset.

defineRoute from the package cannot see a matcher's default. Use apiMatcher.defineRoute for a route that relies on it.

ts
export const listOrdersRoute = apiMatcher
  .defineRoute({ filters: { method: 'GET', path: '/orders' } })
  .handle(async ({ auth }) => orders.list(auth.context.orgId))

A route with no preset, on a matcher with no default, gets the whole APIGatewayAuth union and nothing checks it. A route that needs a claim should use a preset with a claims schema. LambdaAuthorizerMatcher is the other half of this, for writing the authorizer itself.

Lambda authorizer context ​

context holds what your authorizer returned. API Gateway adds its own fields, and nests the context differently on each API. The matcher takes those back out, so you get the same context everywhere.

principalId is set on a REST API only. An HTTP API never passes it on, so it is undefined there.

The values arrive the way your authorizer answered:

AuthorizerValues
REST API, or HTTP API with authorizer payload 1.0Strings, so 3 arrives as '3'
HTTP API with authorizer payload 2.0As returned, including arrays and nested objects

An HTTP API turns every number that is not a whole number into 0, at any depth, whichever payload the authorizer uses. Send a fraction as a string instead. An authorizer written with LambdaAuthorizerMatcher throws rather than send one.

Claims ​

API Gateway hands every claim over as a string, and writes arrays and objects in its own text format. The matcher turns them back into values.

ClaimYour handler gets
exp, iat, nbf, auth_time, updated_atA Date
email_verified, phone_number_verifiedA boolean
cognito:groups, cognito:roles, amrA string[]
audA string, or a string[] when the token names several
addressAn object of strings
Any other claim sent as an array or an objectAn array or an object, with string values
A claim sent as nullnull
Anything elseThe string that arrived

Custom claims keep their names, so a Cognito attribute is claims['custom:tenantId']. A number or a boolean in a custom claim stays a string, because the value no longer says what type it was. That includes Cognito's own Number and Boolean attributes.

An array item that contains a space cannot be recovered. API Gateway writes ['a b', 'c'] exactly like ['a', 'b', 'c'], so your handler gets three items. Put values like that in a single claim holding JSON, and parse it yourself. A plain string that looks like an array, such as '[a b]', is read as an array too. request.event still has it as it arrived.

scopes is undefined on a route with no authorization scopes, even when the token carries some. On a route with scopes it lists every scope in the token. The token's own claim stays in claims.scope.

CORS ​

For an API Gateway you can also configure CORS on the gateway instead, which answers a preflight without invoking your Lambda at all. Doing it here keeps the configuration next to the routes it describes.

createAPIGatewayMatcher takes a cors option, and turning it on covers preflight and every response the matcher sends.

ts
const apiMatcher = createAPIGatewayMatcher({
  cors: {
    origin: 'https://app.example.com',
    credentials: true,  // Optional
    maxAge: 600,  // Optional
    methods: ['GET', 'POST'],  // Optional
    allowedHeaders: ['content-type', 'x-api-key'],  // Optional
    exposedHeaders: ['x-request-id'],  // Optional
  },
})

origin is the only required key.

OPTIONS is answered for you, with a 204 and an Access-Control-Allow-Methods built from the methods you actually registered for that path. A path with a GET and a POST answers GET, POST, OPTIONS, and there is no list to keep in step as you add routes.

The headers go on every response the matcher sends, including a 404, a 400 from a querySchema, a 422 from a bodySchema and anything your handler throws. A middleware could not do that, because it only wraps the handler.

CORS options ​

KeyTypeRequiredDefaultDescription
originstring | string[] | CorsOriginFunctionYesA single origin, a list to match the request's origin against, or a function returning the origin to allow
methodsHttpMethod[]NoThe methods registered for the path, plus OPTIONSOverrides Access-Control-Allow-Methods on a preflight
allowedHeadersstring[]NoWhatever the request asked for in Access-Control-Request-HeadersAccess-Control-Allow-Headers on a preflight
exposedHeadersstring[]NoAccess-Control-Expose-Headers on a non-preflight response

CorsOriginFunction is (origin: string, path: string) => string | undefined | Promise<string | undefined>. Return the origin to allow it and undefined to refuse, which is how you check a tenant's origin against a database. It is only called when the request carries an Origin header.

Vary: Origin is set for any origin that is not *, so a shared cache cannot serve a no-CORS response to an allowed origin. A list or a function that refuses the request still gets Vary: Origin on a non-preflight response for the same reason.

Setting credentials with origin: '*' throws when the matcher is created. Browsers reject that combination, so the constructor refuses it rather than letting you deploy it. In a Lambda that surfaces as an init failure rather than a failing request.

Handling preflight yourself ​

An OPTIONS route wins over the automatic preflight, so you can take over one path and leave the rest alone.

ts
apiMatcher.options({
  filters: { path: '/orders' },
  handler: async () => ({
    statusCode: 204,
    body: undefined,
    headers: { 'Access-Control-Allow-Methods': 'GET, POST, OPTIONS' },
  }),
})

The CORS headers are still added to whatever your handler returns. If the route has a custom that rejects the request, the automatic preflight picks it up instead.

API Gateway event versions ​

One matcher covers all three API Gateway payloads, and it works out which arrived from the shape of the event.

AWS setupPayloadRecognised by
HTTP API2.0rawPath and requestContext.http.method
HTTP API1.0path and httpMethod, the same as a REST API
REST API1.0path and httpMethod

Your handler is given the same request object either way, and the matcher builds the result each payload expects. Nothing else on this page changes with the payload version, so a Lambda can move from a REST API to an HTTP API without touching your routes.

This matcher ignores Lambda authorizer events. The adapter checks for type: 'REQUEST' with methodArn or routeArn before it claims an event. Register it and LambdaAuthorizerMatcher on the same Lambda in any order.

Where the two differ is in what the event itself carries, which is why request.event is typed APIGatewayEvent, a union of both. Narrow it before reading anything payload specific.

ts
// rawPath is only on a 2.0 payload
const payloadVersion = 'rawPath' in request.event ? '2.0' : '1.0'

To take one payload and reject the rest, hand that payload's adapter to HTTPMatcher. Both are exported from here, and the matcher it gives you routes and responds exactly as the one on the rest of this page does.

ts
import { apiGatewayV2Adapter, HTTPMatcher } from '@latcher/apigateway'

const httpApiOnly = new HTTPMatcher({ adapter: apiGatewayV2Adapter })

A payload the adapter rejects is claimed by no matcher, so Latcher throws No matcher found for event. That is an invocation failure rather than a 404, because nothing got as far as routing. Pin a version only where the other arriving is a deployment mistake you want to hear about.

HTTPMatcher takes an adapter on its own as above, or an object with adapter plus the middleware and cors from options. apiGatewayAdapter is the pair of per-payload adapters that createAPIGatewayMatcher uses, so it is the one to pass if you want the default behaviour with something else changed.

ALBMatcher and VPCLatticeMatcher handle the other two HTTP event sources and read the same way, so a Lambda behind both an API Gateway and a load balancer registers one matcher each.

Middleware ​

Matcher and route middleware are both typed HTTPMiddleware, and the chain runs once per request.

ts
import { logger } from '@latcher/base'
import { Unauthorized } from '@latcher/apigateway'
import type { HTTPMiddleware } from '@latcher/apigateway'

export const withApiKey: HTTPMiddleware = async (request, next) => {
  if (request.headers['x-api-key'] !== process.env.API_KEY) {
    logger.warn(`Rejected a ${request.method} with a bad API key`)
    throw Unauthorized()
  }

  return next(request)
}
ts
const apiMatcher = createAPIGatewayMatcher({ middleware: [withApiKey] })

apiMatcher.put({
  filters: { path: '/orgs/:orgId/orders/:orderId' },
  bodySchema: NewOrderSchema,
  middleware: [withOrgContext],
  handler: replaceOrder,
})

A middleware can also short-circuit by returning or throwing an error helper instead of calling next, so an auth check or a maintenance window can answer without the handler running.

The bare alias is the right one for matcher middleware, which runs for every route and so cannot know any one route's shape. That is where a check like the one above belongs.

The bare alias cannot answer with a body of its own, since it runs on routes of every response type. It can return what next() gives it or an error helper, and nothing else compiles. A middleware that reads or builds a body names it as the fifth parameter, so HTTPMiddleware<..., JsonBody> fits only JSON routes and never a matcher.

A route keeps its own types with the bare alias attached. The handler still gets path.orgId from the path pattern and the body from the bodySchema.

The bare alias types each query value as unknown, since a route's querySchema can turn a value into a number or a boolean before the middleware runs.

To read typed values inside the middleware, such as the schema's body, name the parameters in the order TPath, TQuery, TAuth, TBody.

ts
export const withOrgContext: HTTPMiddleware<
  { orgId: string; orderId: string },
  Record<string, string | undefined>,
  APIGatewayAuth,
  NewOrder
> = async (request, next) => {
  logger.appendKeys({ orgId: request.path.orgId, orderId: request.path.orderId })

  return next(request)
}

Neither level runs when nothing matched or when a schema failed. See middleware for the execution order and the three levels it attaches at.

Generic parameters ​

Eight parameters cover every type above, and they do not all appear in the same order.

ParameterTypesDefault

TQueryrequest.queryRecord<string, unknown> on HTTPMiddleware, Record<string, string | undefined> elsewhere
TAuthrequest.authAPIGatewayAuth

ApiRequest, ApiHandler and HTTPMiddleware all start TPath, TQuery, TAuth, TBody. ApiRequest's fifth is TEvent. The other two take TResponse fifth and TEvent sixth. RouteDefinition puts TPathString first and derives TPath from it. It takes TMethod then TEvent last.

Pass only the ones you need up to the last one you care about, so ApiRequest<{ orderId: string }> types the path and leaves the query, auth and body loose.

You only need these for annotated handlers. Inference covers all of them.
